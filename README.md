# Панда Суші — сайт

Статичний сайт на чистому HTML/CSS/JS — **без фреймворків** (React/Vue/Next тощо не використовуються ні на сторінці, ні в збірці). Кожна сторінка — окремий готовий `.html`-файл у корені проєкту, оптимізований під SEO.

## Швидкий старт

Готові сторінки вже лежать у корені (`index.html`, `menu.html` тощо) — можна одразу відкривати їх у браузері або задеплоїти папку `site/` як є.

Якщо потрібно щось змінити (наприклад, текст у шапці чи підвалі, або вміст сторінки):

```bash
npm run build
# або напряму:
node build/build.js
```

Це перегенерує всі `*.html` у корені з файлів у `src/`. Node.js (будь-яка сучасна версія) — єдина залежність, `npm install` не потрібен: скрипт збірки не використовує жодних npm-пакетів.

## Структура проєкту

```
site/
├── index.html, menu.html, ...   ← ГОТОВІ сторінки (результат збірки, це і є сайт)
├── favicon.ico, robots.txt, sitemap.xml, site.webmanifest
│
├── src/                         ← ВИХІДНИКИ, з яких генеруються сторінки
│   ├── partials/
│   │   ├── header.html          ← шапка сайту (та сама на всіх сторінках)
│   │   └── footer.html          ← підвал сайту
│   ├── pages/
│   │   ├── index.html           ← вміст головної (без шапки/підвалу — їх додає build.js)
│   │   ├── menu.html
│   │   └── ...                  ← по одному файлу на кожну сторінку сайту
│   └── schema/
│       ├── restaurant.json      ← Schema.org розмітка (LocalBusiness/Restaurant)
│       └── article.json         ← Schema.org розмітка для статті блогу
│
├── build/
│   └── build.js                 ← скрипт збірки (Node.js, без залежностей)
│
├── assets/
│   ├── css/                     ← стилі, ОКРЕМИЙ файл на кожен розділ
│   │   ├── base.css             ← reset + дизайн-токени (кольори/шрифти/відступи) — підключений скрізь
│   │   ├── fonts.css            ← @font-face, шрифти Manrope + Prata
│   │   ├── header.css / footer.css / cart.css  ← спільні для всіх сторінок
│   │   └── home.css, menu.css, rolls.css, ...  ← стилі конкретної сторінки
│   ├── js/
│   │   ├── common.js            ← мобільне меню, кошик/обране (localStorage) — підключений скрізь
│   │   ├── forms.js             ← обробка форм-заглушок (контакти, вакансії тощо)
│   │   └── rolls.js, article.js, promotions.js  ← JS конкретної сторінки
│   ├── fonts/                   ← файли шрифтів (.woff2), розміщені локально
│   ├── images/                  ← фото страв, іконки
│   └── images/icons/            ← favicon.svg, apple-touch-icon.png, icon-192/512.png
│
└── server/
    ├── nginx.conf.example       ← приклад конфігурації Nginx (security-заголовки, кешування, gzip)
    └── .htaccess                ← те саме для Apache
```

## Як влаштована збірка сторінок

`build.js` — це **не фреймворк і не рантайм-залежність**: він виконується один раз під час розробки (`npm run build`) і на виході дає звичайні статичні `.html`-файли. У браузері користувача виконується вже тільки чистий HTML/CSS/JS — жодного Node.js, React чи іншого рантайму на клієнті немає.

Навіщо він потрібен: шапка й підвал однакові на всіх 14 сторінках. Без збірки довелося б вручну копіювати їх у кожен файл і синхронізувати зміни в 14 місцях. Замість цього:

1. Кожен файл у `src/pages/*.html` містить **лише унікальний вміст** сторінки (без `<html>`, `<head>`, шапки, підвалу).
2. Нагорі файлу — HTML-коментар із простими `ключ: значення` (frontmatter): заголовок, опис, canonical-URL, які CSS/JS підключити.
3. `build.js` бере цей вміст, вставляє спільну шапку (`src/partials/header.html`) і підвал (`src/partials/footer.html`), формує `<head>` з SEO-тегами — і зберігає результат як звичайний `.html`-файл у корені.

**Щоб змінити сторінку:** редагуйте файл у `src/pages/`, потім запустіть `npm run build`.
**Щоб змінити шапку чи підвал:** редагуйте `src/partials/header.html` або `footer.html`, потім `npm run build` — оновляться всі 14 сторінок одразу.
**Ніколи не редагуйте** готові `.html`-файли в корені напряму — їх перезапише наступна збірка.

### Формат frontmatter

```html
<!--
title: Заголовок сторінки — Панда Суші
description: Опис для META description і Open Graph
canonical: /menu.html
ogImage: /assets/images/home/hero-set.jpg
bodyClass: page-menu
css: menu           (список файлів з assets/css/ через кому, без .css)
js: rolls            (список файлів з assets/js/ через кому, без .js)
schema: restaurant.json  (необов'язково — JSON-LD файл з src/schema/)
noindex: true         (необов'язково — додає <meta name="robots" content="noindex">)
-->
<!-- далі йде звичайний HTML-вміст сторінки -->
```

`base.css`, `fonts.css`, `header.css`, `footer.css`, `cart.css` підключаються автоматично на кожній сторінці — вказувати їх у `css:` не потрібно.

## Чому кожна сторінка — окремий `.html`-файл

Це осмислене SEO-рішення, а не обмеження: кожна сторінка (`/menu.html`, `/rolls.html`, `/philadelphia.html` тощо) має власний `<title>`, `description`, `canonical`, Open Graph-теги й іноді власну Schema.org-розмітку. Пошукові системи індексують кожну сторінку окремо з унікальними сніпетами — на відміну від SPA на одному `index.html`, де без додаткового SSR/prerendering сторінки для пошуковика виглядають однаково.

## Дизайн-система

- **Кольори, шрифти, відступи** — CSS-змінні в `assets/css/base.css` (`:root { --color-accent: ...; }`). Змінюйте значення тут — оновиться весь сайт.
- **Шрифти** — Manrope (текст) і Prata (заголовки), самостійно розміщені (self-hosted) в `assets/fonts/`, а не підключені через `fonts.googleapis.com`. Це і швидше (менше зовнішніх запитів), і приватніше (Google не бачить IP відвідувачів).
- **Повторювані блоки** (картка товару `.product-card`, хлібні крихти `.breadcrumbs`, FAQ-акордеон `.menu-faq-item` тощо) навмисно винесені в спільні CSS-класи й перевикористовуються на кількох сторінках — щоб змінити вигляд картки товару, достатньо відредагувати один файл (`assets/css/home.css`).

## Кошик, обране, форми — як це працює без бекенду

Бекенду немає — це чистий фронтенд. Тому:

- **Кошик і обране** (`assets/js/common.js`) зберігаються в `localStorage` браузера — працюють по-справжньому (додавання, кількість, видалення), але тільки в межах одного браузера на одному пристрої. Кнопка «Оформити замовлення» формує лист на `hi@pandasushi.od.ua` через `mailto:` із переліком товарів — це чесний робочий варіант без бекенду, не імітація успішного замовлення.
- **Форми** (зворотний зв'язок, відгук на вакансію, «питання шефу») — `assets/js/forms.js` перехоплює відправку, перевіряє поля (включно з honeypot-полем проти ботів) і показує чесне повідомлення, що бекенду поки немає, з прямим контактом (телефон/email). Дані нікуди не надсилаються.
- **`TODO(бекенд)`** — позначка в коді `forms.js` там, де потрібно підключити реальний `fetch()` до сервера, коли бекенд з'явиться.
- **Особистий кабінет** (`/account.html`) — демо-перегляд інтерфейсу з прикладними даними, це прямо написано банером на самій сторінці. Реальної авторизації (вхід за SMS-кодом) немає навмисно — фейковий «успішний вхід» без сервера був би оманливим.

## SEO, що вже налаштовано

- Унікальні `title`/`description`/`canonical`/Open Graph на кожній сторінці
- `sitemap.xml` і `robots.txt` у корені (домен `https://pandasushi.od.ua` — замініть у `build.js`, `sitemap.xml`, `robots.txt` і `src/schema/*.json`, якщо домен інший)
- Schema.org JSON-LD: `Restaurant` (головна, контакти) і `BlogPosting` (стаття блогу)
- Семантична розмітка (`<nav>`, `<article>`, `<h1>`–`<h3>` без пропусків рівнів, хлібні крихти)
- Зображення з `width`/`height` (щоб не «стрибав» вміст під час завантаження) і `loading="lazy"` для всього, крім hero-зображення
- `alt`-тексти на всіх фото

## Безпека

- **CSP, HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy** — налаштовуються на рівні сервера, приклади в `server/nginx.conf.example` і `server/.htaccess`. Через HTML-теги ці заголовки повноцінно не працюють (частина з них, як-от HSTS чи X-Frame-Options, взагалі ігнорується браузером у `<meta>`), тому конфігурація сервера — обов'язковий крок перед публікацією.
- Жодних інлайн-обробників подій (`onclick="..."`) у розмітці — увесь JS підключається файлами й вішає обробники через `addEventListener`. Це дозволяє тримати `script-src` у CSP без `'unsafe-inline'`.
- Форми захищені honeypot-полем (приховане поле, яке заповнюють тільки боти) — без CAPTCHA і зовнішніх залежностей.
- Зовнішні посилання (`target="_blank"`) мають `rel="noopener noreferrer"` — захист від `window.opener`-атак.
- Персональні дані (кошик, обране) зберігаються тільки локально в браузері користувача — на сервер нічого не надсилається, окрім явних дій користувача (клік «Оформити замовлення» → mailto).

## Відомі обмеження й що покращити далі

- **Кешування статики без хешування імен файлів.** CSS/JS підключені за постійними іменами (`/assets/css/home.css`), тому в `server/nginx.conf.example` кеш свідомо помірний (7 днів). Щоб безпечно ставити кеш на рік, додайте у `build.js` крок хешування імен файлів (наприклад, `home.a1b2c3.css`) під час збірки.
- **Зображення — тільки JPEG.** Конвертація в WebP/AVIF дала б додатковий виграш у вазі; не зроблено зараз, бо вимагало б окремого інструменту стиснення зображень.
- **Каталог ролів показує 7 реальних позицій**, хоча в текстах згадуються «48 видів» — це маркетингове число з вихідного дизайну. Основні реальні фото (Філадельфія, Каліфорнія, Дракон тощо) представлені по всьому сайту послідовно; решту асортименту варто наповнити разом із реальним меню/бекендом.
- **Особистий кабінет і форми — без бекенду.** Дивіться розділ вище.

## Технічна оптимізація "з коробки"

- Шрифти `font-display: swap`, самостійно розміщені, підвантажуються без сторонніх запитів
- `fetchpriority="high"` на hero-зображеннях, `loading="lazy"` на решті
- Жодного зовнішнього JS/CSS (жодних CDN-залежностей) — усі ресурси з одного домену, менше DNS/TLS-з'єднань
- Логотип — чисті CSS-фігури (кола), без зображення
- Favicon у трьох форматах (SVG, ICO, PNG 192/512) — жодних 404 на іконки
